## 12. End-To-End Testing

The repository should provide `npm run test:e2e` as a separate, opt-in quality
gate for slow and potentially paid real-agent testing. The e2e suite MUST run
the public TypeScript library API against real local CLI processes and real
PTYs, minimizing mocks and seams. It should verify the critical library flows
for each installed/authenticated supported adapter: start, terminal output,
raw input, prompt/message submission, hook observation, activity observation,
resize, stop, resume when the adapter reports a resume id, kill/teardown, and
Elwood-owned state cleanup.

`test:e2e` may skip an adapter when its CLI is not installed or cannot pass a
basic version/authentication preflight, but it should not use fake PTYs, fake
hook bridges, or fake agent processes for the adapter flows it does run. Because
the suite depends on local auth, network, model availability, and user-installed
CLIs, it is intentionally separate from `npm run check`. E2E coverage should be
reported separately and made as high as practical; unit/conformance tests remain
responsible for hard-to-force error paths and 100% default coverage.

Neither gate may write the developer's own Codex home or read its state; the e2e
suite only copies its `auth.json`. By default, every `test:e2e` process runs with
`CODEX_HOME` pointed at a private directory seeded with only a 0600 copy of that file,
removed when the process exits. A single e2e file run on its own gets the same default.
A test that needs its own Codex config uses another private home, seeded the same way,
for its duration. Whichever private home is active receives the project trust entries,
model selections, sessions, and logs Codex persists while the suite drives it, so none
of them reach the developer's config. The default gate runs each test file with `HOME`
and `CODEX_HOME` pointed at a private directory. Both gates refuse to create these
homes when the temp directory is inside the developer's Codex home.

The e2e suite may not write the developer's own Claude config either. By default,
every `test:e2e` process, and a single e2e file run on its own, runs Claude with
`CLAUDE_CONFIG_DIR` pointed at a private directory, removed when the process exits.
It is seeded with three copies: a 0600 `.credentials.json` holding the developer's
Claude login without its refresh token, so the copy can never rotate and so
invalidate the developer's own login. The login is read from where the developer's
own Claude reads it. On macOS that is the keychain item Claude names for the developer's
`CLAUDE_SECURESTORAGE_CONFIG_DIR` when it is set, else for their `CLAUDE_CONFIG_DIR`,
set or not, and their `.credentials.json` only when there is no such item. On other
platforms it is the `.credentials.json`. The suite removes
`CLAUDE_SECURESTORAGE_CONFIG_DIR` from its own environment, so the Claude it runs
reads the private copy, never the developer's item. The second copy is the developer's
global config without its per-project entries, MCP servers, or bypass-permissions
acceptance, and the third is Claude's cached model catalog. The global-config
entry Claude writes for each scratch project, its transcripts, and its history land
there, never in the developer's `~/.claude.json` or `~/.claude/`, which are only read.
The private directory holds none of the developer's settings, so the suite runs Claude
with Claude's defaults rather than the developer's permission mode, hooks, or plugins.
The suite refuses to create it when the temp directory is inside the developer's Claude
config dir.
A test that needs its own Claude config dir copies the login the same way, without the
refresh token.

Both CLIs start through the developer's login shell, whose startup files run after
Elwood hands over its environment and could replace, unset, or unexport `CODEX_HOME` or
`CLAUDE_CONFIG_DIR`. So the suite registers each private CLI home it creates in
`ELWOOD_E2E_PRIVATE_HOMES`, a JSON array of absolute paths holding each home's given and
real path, which the Elwood processes it starts inherit. Each e2e process discards the
list it inherited and registers only the homes it creates, so an inherited entry, such as
the developer's own home, is never accepted. Each of the two variables that
Elwood's own environment sets to a registered home is guarded. Every login shell Elwood
starts, for a session or a probe, checks after its startup files that each guarded
variable is still exported and that the real path of the directory it names, relative
names resolved against the shell's working directory, is a registered home. If one is
not, the shell writes a stop line with why and exits 97 before running its command, so
no CLI starts against another home, the developer's own included. A value that is not
such an array stops every launch the same way. Unset or empty, as outside the suite, the
variable changes nothing.

The stop line starts with a token Elwood draws once per process, so neither a startup
file nor a command can print it. It is never written to stderr, which a startup file can
redirect. A session's shell writes it to its terminal, which the session's PTY captures
however the startup files redirected the shell's input and output, and falls back to
stdout only when it cannot open the terminal. A probe's shell runs in a session of its
own, with no terminal, so it writes the line to the stdout the probe captures.
Elwood counts a launch as stopped by the guard only when its shell exited 97 and wrote
that line. A command that itself exits 97 is the command's own failure. A session's
startup check (§9.1) finds the line however much startup output came before it. Since a
PTY's last output can arrive after its exit (§9.4), once the check sees a status-97 exit
of a launch the guard checks, it waits up to one second more for the line; a launch the
guard does not check fails at once.

A probe runs the check after its start line (§9.2). A probe the guard stops after that
line is a login-shell failure (C-PERF-05) whose only diagnostic is the guard's fixed
reason: like any login-shell failure, its stderr is withheld. A login shell that exits
before the start line is still the login shell's own failure. A session whose login
shell the guard stops during startup (§9.1) fails with the adapter's `*_start_failed`,
whose message names the guard instead of repeating the shell's output. A session stopped
later exits with status 97, its terminal showing the stop line and the guard's reason.

The repository should also provide `npm run check:all`, an opt-in convenience
gate that runs the default `npm run check` gate and then `npm run test:e2e`.
`check:all` does not change the composition of `npm run check`; the default gate
remains free of real-agent dependencies.
