## 5.1 Starting Claude

```ts
export type LaunchEnvironmentOverrides = Readonly<Record<string, string | undefined>>;

type StartClaudeOptions = {
  readonly cwd: string;
  readonly env?: LaunchEnvironmentOverrides;
  readonly stateDir?: string;
  readonly name?: string;
  readonly initialSize?: TerminalSize;
  readonly hooks?: ClaudeHookHandlers;
  readonly persona?: string;
  readonly model?: string;
  readonly reasoningEffort?: ClaudeReasoningEffort;
  readonly fastMode?: boolean;
  readonly permissionMode?: ClaudePermissionMode;
  readonly allowedTools?: readonly ClaudeToolRule[];
  readonly disallowedTools?: readonly ClaudeToolRule[];
  readonly tools?: readonly ClaudeToolRule[];
  readonly settingsOverrides?: ClaudeSettingsOverrides;
  readonly highTrust?: boolean;
  readonly autoupdate?: boolean;
  readonly autotrust?: boolean;
  readonly hookTimeoutMs?: number;
  readonly strictVersionCheck?: boolean;
};

type ClaudeReasoningEffort = "low" | "medium" | "high" | "xhigh" | "max";
declare const claudeReasoningEfforts: readonly ["low", "medium", "high", "xhigh", "max"];

declare function startClaude(options: StartClaudeOptions): Promise<ClaudeSessionApi>;
```

`claudeReasoningEfforts` is exported from the package entrypoint as an immutable
tuple for hosts that populate an effort selector. Its values match
`ClaudeReasoningEffort`; effort remains a separate `reasoningEffort` launch
setting rather than part of a model id. The tuple names accepted CLI values,
not a guarantee that every model supports each level.

`env` overlays the inherited child environment for this launch: string values set
variables and `undefined` removes them. Elwood snapshots that effective environment
before preflight and uses it for its version/update probes and the agent's login shell,
without changing the host's `process.env`. Login profiles may still change the
child's environment. Elwood's own `ELWOOD_SESSION_ID` overrides a supplied value.
The option is not persisted; resume must re-supply it. Probe results from different
effective environments are not shared. The process-wide updater deduplication
remains per adapter; its first attempt uses that caller's environment.

`cwd` is the initial PTY working directory. It MUST already be a
directory: otherwise `startClaude` rejects with `claude_start_failed`, whose
`details` carry `cwd` and the failed check's `errno` (`ENOENT`, `ENOTDIR`, or,
when the check itself fails, its own code such as `EACCES`), before it runs any
probe, writes any state, or spawns Claude. A relative `cwd` is resolved against
the process working directory when `startClaude` is called; one that can't be,
because that directory was deleted, rejects the same way, with `cwd` as given.
Because `cwd` can be removed or replaced while the probes run, its identity from
before preflight is checked again afterward, before any state is written or PTY
spawned. A replacement rejects with `claude_start_failed` and `details.cwd`, without
an `errno`. A launch that fails while `cwd` is
gone, no longer a directory, can't be checked, or is no longer the directory
that check found (it was deleted and made again) rejects the same way, keeping
the failed launch's `cause` and any cleanup details (§9.1, §10). Elwood never
creates it: a state directory is made only while `cwd` exists, one at or under
`cwd`, the default `<cwd>/.elwood` or a caller's own, only below it, and no
state write makes a missing parent (§8.1, C-STATE-14), so a deleted worktree is
not silently recreated empty (C-API-61).
The PTY child also checks that original directory before profiles and after
profiles, before the CLI command (§4.2). Profiles may deliberately `cd`; a
replacement restored between these bounded checks may escape detection, and
executable selection is not atomic.
`stateDir` overrides
the default Elwood state directory. `name` is a launch-time convenience forwarded
to Claude's documented `--name` flag; it is not persisted in Elwood state (§8.2).
`hooks` registers
launch-time handlers before Claude starts. When `autoupdate` is true, Elwood
runs `claude update` from the user's login shell before spawning Claude and
rechecks the version after the update. The update command runs at most once
per parent process per adapter, so a parent spawning a roster of sessions at
launch does not run N concurrent same-binary updates (C-LIFE-09); later
sessions in the same process reuse the already-updated binary. Separate Elwood
parent processes for the same macOS user also coordinate through an atomic,
per-adapter lease in a stable account cache independent of each process's temporary
directory: one process runs the global updater while contenders wait asynchronously
for it to finish, then skip their duplicate attempt and re-read the installed
version. The lease records its owner and generation; an old owner cannot remove a
successor's lease, a live owner is never evicted solely because of elapsed time,
and a crashed owner's stale lease is recoverable after a fixed bound longer than
the update probe's own timeout. `strictVersionCheck` makes unparseable Claude
versions fatal instead of warning-and-continuing. `permissionMode`
accepts Claude's documented launch values: `default`, `acceptEdits`, `plan`,
`auto`, `dontAsk`, and `bypassPermissions`.

`highTrust` is the agent-neutral "never ask for permissions" switch. On Claude,
`highTrust: true` expands to `permissionMode: "bypassPermissions"` before the
posture is persisted or the process is spawned, so the record, `config
effective`, and the launched CLI all agree. It is an expansion, not a second
axis: supplying an explicit `permissionMode` together with `highTrust: true` is a
configuration error rejected before spawn with the typed
`claude_high_trust_conflict` error. When Claude starts in bypass-permissions
mode it may render a one-time acceptance dialog (header `WARNING: Claude Code
running in Bypass Permissions mode`, affirmative `Yes, I accept`, decline `No,
exit`); that dialog is an allowlisted trust prompt answered under `autotrust`
with `startup_prompt` label `bypass_permissions`, and with `autotrust` off it is
a blocking prompt like any other trust gate. Whether the installed CLI shows the
dialog at all is version- and machine-dependent (the CLI may persist the
acceptance), so Elwood answers it when present and otherwise proceeds. When the
CLI itself refuses bypass mode (for example when running as root), Elwood does
not special-case it: the refusal surfaces as the ordinary start failure carrying
the CLI's own message.

`model` is forwarded to Claude's documented `--model` launch flag so the
session starts on the requested model. Elwood does not validate the value;
Claude owns model-name resolution and its own failure behavior.

`reasoningEffort`, when set, is forwarded to Claude's documented `--effort`
launch flag so the session starts at the requested reasoning effort. Unlike
`model`, the value is a fixed per-CLI enum, so Elwood validates it against the
`ClaudeReasoningEffort` set BEFORE spawning and rejects an out-of-enum value with
the typed `claude_invalid_reasoning_effort` error (listing the valid values), so a
typo fails fast at start rather than deferring to the CLI. The effort applies to
the current session only and is NOT persisted by Elwood; a resumed session must
re-supply it (§5.2), consistent with `model`. Reasoning effort and model are
independent axes on Claude (the flag is separate from `--model`).

`autotrust` is an opt-in convenience for embedded/headless parent apps.
When true, Elwood detects Claude's first-party workspace trust prompt in the
rendered terminal and chooses the trust/continue option through PTY input. The
default is false because trusting a workspace is a security-sensitive decision.
When Elwood answers the prompt, the session emits adapter-neutral
`startup_prompt` activity with label `workspace_trust`.

Separately from `autotrust`, Elwood MUST dismiss Claude's non-security
first-party onboarding prompts that would otherwise block readiness or input in
an embedded session, always choosing the option that declines or defers the
offered capability. The currently known prompts of this kind are:

- The browser tools onboarding prompt, declined through PTY input (Escape) with
  `startup_prompt` activity emitted under the label `browser_tools`.
- The auto-mode setup offer (`Teach auto mode about your environment?`, §5.3),
  which Claude can show after a turn. Elwood declines its first menu through
  PTY input (Escape), which chooses `Not now`; Claude then defers the offer for
  7 days. Claude ignores a choice made less than 500 ms after the menu first
  renders or after the previous attempt, so Elwood sends the first Escape
  750 ms after it first sees the menu and repeats it 750 ms apart, at most four
  times, until a settled frame no longer shows the menu. Only that verified
  dismissal emits `startup_prompt` activity, under the label
  `auto_mode_setup`. If a settled frame still shows the menu after the fourth
  Escape, Elwood reports nothing more and leaves that appearance, with the
  session `blocked` on its attention label, to the human. Raw caller input while
  the menu is on screen hands that appearance to the human, and Elwood never
  declines the setup step that `Yes` opens. While an offer Elwood is not
  declining stays on screen, the session's status is `blocked`, its `attention`
  activity carries the label `claude-auto-mode-offer` (§5.3, C-ATTN-09), and
  each queued send, `send()` and `stream()` included, waits behind it with
  nothing written. A held send has no timeout of its own: an ergonomic
  `timeoutMs` starts only at the submitting Enter (§5.8). The send proceeds once
  the offer closes, for example after the caller answers it through `sendKeys`.

This automation is unconditional because declining grants nothing and an
unanswered onboarding prompt permanently wedges a headless session.

This non-trust automation has the SAME lifetime as trust automation: it is bound
to session disposal. Once the session begins closing — `stop()`, `kill()`, or PTY
exit — no further decline is attempted, and a decline already in flight settles as
a cancellation. Because the non-trust automation barrier parks on render settlement,
a write suspended there re-checks disposal when it resumes and abandons the keystroke:
nothing is written to a terminated PTY, and neither `startup_prompt` nor
`startup_prompt_write_failed` is emitted after close.

`persona` is an optional instruction message for the agent. A persona exceeding
8 MiB of UTF-8 text rejects startup with `input_queue_full` before preflight,
state creation, or process spawn. When set within this limit, Elwood
enqueues it before control returns to the caller, so it is guaranteed to be the
session's first submitted user message: it is delivered through the standard
message queue as soon as the session first becomes ready, ahead of any
caller-queued messages. Persona delivery is observable through the normal hook
and activity events, exactly like a caller-submitted message. The persona is
not persisted in Elwood state (§8.3 applies) and is not re-sent on resume. If
the session terminates before ever becoming ready, the undelivered persona is
discarded silently.

Speed options and raw override behavior are specified in [§5.11](5.11-speed.md).
