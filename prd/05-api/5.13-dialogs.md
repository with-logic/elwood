# 5.13 Native dialog discovery

Eager and lazy Claude and Codex sessions expose
`listDialogs(): Promise<readonly ElwoodDialogRequest<Agent>[]>`, with `Agent`
equal to `"claude"` or `"codex"` for their respective sessions. The public
`ElwoodDialogRequest` type defaults to `"codex"`. Calling the lazy method
starts the session if needed. The list contains a complete native workspace
trust request while it blocks startup for a human decision. Automatic trust
policies still control their own prompts until raw caller input takes over
or the current automation attempt expires. An active Codex `dialog` listener
can receive a newly human-owned prompt without another redraw. A Codex list
can also contain the update offer that
[Codex update offers](#codex-update-offers) describes.

`ElwoodDialogRequest` is a union discriminated by `kind`. A workspace trust
request, exported as `ElwoodTrustDialogRequest`, has readonly `id`,
`elwoodSessionId`, `agent: "claude" | "codex"`, `kind: "trust"`,
`label: "workspace_trust"`, `targetPath`, `targetScope: "folder" | "repository"`,
`text`, and `choices` in native display order. Each choice contains an opaque
`id` and the native `label`. The `text` contains the native question and
explanation with whitespace folded. A Claude explanation with the permissions
warning (§5.4) includes the folder's rules as Claude draws them: text the folder
chose, not Claude. Use `targetPath` and `targetScope` for
the exact trust target. A Claude request also has `disclosesHooks`. It is
`true` when the prompt disclosed hooks with its hooks rows (§5.4): trusting the
folder runs commands its project settings configure. `false` means only that the
prompt disclosed none. It never means the folder has no hooks: a Claude older
than 2.1.329 cannot disclose them, and a load row naming settings files alone can
enable plugins whose hooks run as the session starts (§5.4). The field is on the Claude request alone:
narrowing a request's `agent` to `"claude"` exposes it. A Codex request has no
such field, because Codex's prompt never says whether the folder has hooks. Redraws, unsettled repaints and cursor movement retain
the request and choice IDs during one continuous appearance. A settled frame
that no longer shows the menu ends that appearance.

Discovery requires a complete layout in settled native PTY output and an
independently verified launch folder or repository root. Elwood captures the
scope before spawning the CLI and revalidates it for the read. Overlapping
list reads may share a pending check for the same frame. Each optional
evidence lookup allows up to 500 ms. A timed-out list or publication check ends discovery if its native frame and
lookup are still current. If another frame has superseded it, the newer
frame can be checked. If two expired filesystem checks are still waiting for
the OS, a new check requires a poll after one finishes. Unavailable evidence,
ambiguous paths and unsupported
layouts leave the existing native hold in effect. For Claude, losing
verification of the launch path or Git scope retires discovery for that launch.
Claude can wrap the path across rows in a narrow terminal. Discovery accepts
it only when the native wrap margins are intact and the rows reconstruct the
exact checked launch path. For a numbered Claude menu, the two options must
be numbered 1 and 2 in display order, with one marked selection.
Host output injected via
`terminal.writeOutput()` or direct xterm writes, host clears and resets, and
a size change after PTY output begins revoke native discovery
evidence for the life of that terminal. Scrollback selection does not affect
discovery. Positive native composer clearance or session closure ends the
startup discovery window.

Each list call checks that the verified frame is still current before returning
the request or an empty array. Unsettled output or an outstanding list proof for
an older frame can temporarily yield an empty list. Listing does not flush pending
terminal output. Codex listing does not wait for event delivery. Hosts can
respond through the terminal or submit a verified choice with `answerDialog()`
when automatic trust is off, as it is by default. Codex can keep an expired automatic
prompt listable for native input.
Ordinary prompt submissions stay held until the native gate clears.

## Codex dialog events

A `dialog` event has a request and `phase: "raised" | "closed"`. Elwood verifies
`raised` before dispatch. Listeners registered at dispatch start that are still
registered when called receive the same immutable snapshot. Changes made by a listener affect later reads and
deliveries. Buffered lazy listeners attach before the initial dispatch and share
its snapshot. A listener attached after an announcement receives a separately
verified `raised` replay of the still-current request after registration returns.
During a repaint, replay waits for settled
native output to verify the same request. Unsubscribing or retiring the request
cancels pending replay.

Retirement takes effect immediately. A subsequent `closed` event reports a
request previously raised by the session. A listener can receive `closed` even
if it did not receive that request’s `raised` event. Reasons are `"cleared"` for native composer clearance,
`"replaced"` for a different supported layout or target in settled native output,
or `"unavailable"` for lost evidence or session closure. A replacement gets
its own verification after `closed` dispatch before it can be raised. Listener
failures do not interrupt terminal processing.

Each `raised` dispatch and late replay requires an independent proof. Event
checks start only with a subscriber. Unsubscribing cancels the pending replay
or the last subscriber’s check. In-flight OS calls can finish later, and
publication coalesces checks while two publication lookups remain outstanding.
An ordinary redraw of an announced request needs no event check when no replay
is pending. See [§5.4](5.4-events.md) for diagnostics when a dialog listener fails.
Update offer events follow [Codex update offers](#codex-update-offers) instead.

## Claude dialog events

Eager and lazy Claude sessions emit a typed `dialog` event with the verified
request and `phase: "raised" | "closed"`. Closed events include a `reason`.
Use `cleared` for verified composer clearance, `replaced` for another supported
native trust menu, and `unavailable` if evidence is lost, a settled layout
cannot be verified, or the session closes.

Each announcement and retained replay verifies the exact current frame and
its scope with a fresh check. Event checks run while listeners are subscribed.
An unchanged announced menu needs another publication check when a replay is
pending. List and event reads collect separate proofs under the same limit of
two unfinished filesystem checks. If both slots are in use, publication
checks the latest frame when a slot opens. A list can return empty in that
case and the caller can poll again. If a dialog callback runs during a pending
list check, the list checks scope again.
A new listener receives a still-current active request after registration
returns. Replay waits through an unsettled repaint and resumes if the same
menu becomes current. Unsubscribing or retiring the request cancels replay. A
listener whose replay is canceled by retirement can receive `closed` alone.
A snapshot error during the first publication leaves independent list checks
available when the viewport becomes readable again. The native menu remains
available for input while optional discovery is unavailable. Listener failures
do not interrupt terminal processing. See [§5.4](5.4-events.md) for diagnostics.

## Codex update offers

A Codex session lists Codex's in-TUI update offer ([§5.5](5.5-starting-codex.md))
while no Elwood skip answers it. That happens after raw caller input takes the
offer over, after the skip's bounded retries end with the offer still drawn,
or when the offer has no safe choice. While a skip is pending, the list omits
the offer. The request, exported as `ElwoodUpdateDialogRequest`, has readonly
`id`, `elwoodSessionId`, `agent: "codex"`, `kind: "update"`,
`label: "codex_update"`, `text`, and `choices`. Like `workspace_trust`, the
label names what the answer acts on, here Codex itself. When the banner names
the versions it also has `versions: { installed, offered }`. The `text` is the
banner and the rows before the choices, with whitespace folded to single
spaces, so a link Codex wraps can contain a space. Each choice has an opaque
`id` and the native label in display order, `Update now` included.

Discovery reads settled native PTY output that shows a recognized first-party
banner and one valid native choice block (§5.5). Cursor movement and redraws
with the same text and labels keep the request and choice IDs. Unsettled
output keeps the current request. A settled frame without the offer, a
different offer, or a new skip of the offer ends the request. Host output
injected via `terminal.writeOutput()`, host clears and resets, and a size change
after PTY output begins end update discovery for the life of that terminal.
The first readiness and session closure end the startup discovery window.

The session emits a `dialog` event with `phase: "raised"` when discovery first
identifies a request, without waiting for a `listDialogs()` call, and
`phase: "closed"` when the request ends. Events are dispatched in
order after the terminal processing that changed the request. Listeners
registered at dispatch share one immutable snapshot. A listener attached after
an announcement receives a `raised` replay of the still-current request after
registration returns. Ending the request or unsubscribing cancels the replay,
and that listener can receive `closed` alone. The closed reason is `"cleared"`
when a settled frame no longer shows the update banner, which on Codex 0.172.0
can be its header alone before the composer. It is `"replaced"` for a different
offer. Any other end is `"unavailable"`: a new skip, a banner left without a
complete choice block, lost native evidence, the end of the startup window, or a
discovery failure. A listener that a replayed listener adds waits for the next
delivery, which reads the frame again. Listener failures do not interrupt
terminal processing. They produce the content-free warning that
[§5.4](5.4-events.md) describes. A failure in update discovery itself, including
one after a skip settles, produces the `frame_observer_failed` warning of
§5.4 and ends update discovery for the session.

Hosts answer the offer at the native terminal. `answerDialog()` with an update
request ID rejects with `dialog_not_found`.

Claude Code draws no update screen in its TUI
([docs/cli-behavior.md](../../docs/cli-behavior.md)). Claude sessions never list
or announce a `kind: "update"` request, and `ElwoodDialogRequest<"claude">`
excludes it.

## Codex workspace trust answers

Call `answerDialog(requestId, choiceId, { timeoutMs?, signal? })` with IDs
from a verified request. The timeout defaults to 12,000 ms and must be finite
and positive. Both controls apply after lazy startup. The promise reports
native acceptance, Back, Quit, or a typed failure (§10). The failure category is
`frame` if the deadline expires before confirmation and `native_acceptance`
if confirmation was already dispatched.

Before each Up, Down or Enter, Elwood verifies the current settled native
frame, request and launch scope. The proof begins after any synchronous
dialog delivery returns. A callback delivered during proof revokes that
proof. If navigation has already started, Elwood can recheck the unchanged
frame after delivery within the original answer deadline. Navigation requires
a new frame after each key. At most two
unfinished filesystem checks can coexist in the session's list/answer pool.
A timed-out lookup for the current answer rejects it with `frame` and leaves
list proof available, including after navigation.
A verified scope mismatch retires the outdated request. Retirement ends any
answer navigation still using that request.

Structured Codex answers require automatic trust to be disabled. An expired
automatic prompt can still be listed for native input, but attempting a structured
answer returns `dialog_not_found`. Raw startup input or an answer failure after
attempting a key revokes structured input for the rest of that startup. Listing and the native terminal remain available
when their own evidence is current.

Affirmative selection needs a verified native composer or complete Codex hook
review. Quit needs a native process exit with code zero, no terminating
signal, and settled native evidence for the selected Quit. Elwood lets native
output already received settle within the terminal drain limit and the original
answer deadline. A replacement or loss of that evidence prevents confirmation.
Back needs the native Agent Command Center
and keeps ordinary input held. Back retires the answered request, and a later
verified workspace prompt can be listed and announced. A different complete
native trust menu revokes an outstanding confirmation. Host output or a viewport
mutation revokes these proofs. Elwood observes native confirmation before the
ready callback. Codex can save affirmative
trust for the disclosed target in its effective `CODEX_HOME`.
