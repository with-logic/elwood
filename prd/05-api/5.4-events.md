## 5.4 Events

The primary event API is typed event-emitter style.
Each live event delivery or hook-specific response dispatch considers the
registrations present at its start. If a registration is removed before its
callback runs, the dispatch skips it. Re-registering the same handler joins
future dispatches. Hook-specific response dispatch follows generic hook and
activity notifications. A `status` listener that throws does not skip that
status's `activity`. A listener that throws while Elwood observes a rendered
frame, such as a `status` listener or an `activity` listener for the `attention`
activity of a dialog that frame shows, does not stop the frame's other
notifications: its status and attention activities are still delivered,
readiness still observes the frame, and Elwood still delivers its
`terminal:data`. The first failure while observing a frame produces one live
`frame_observer_failed` warning per session and its normalized warning activity,
with `source: "lifecycle"`, `severity: "warning"`, the session ID and agent,
message `"A rendered-frame notification failed."`, and raw diagnostic
`"frame_observer_failed"`. It carries no exception or screen content. A failure
observed while the session starts, before start or resume returns, is delivered
after it returns, as other startup warnings are (C-API-14). Reporting ends when
the session starts closing, and failures in diagnostic listeners do not
recursively warn (C-API-72).

Required event families:

- `terminal:data`: raw PTY output bytes/string for live rendering.
- `terminal:exit`: PTY process exit.

`resize` should update both terminal models while the process is alive. If the
native PTY reports that its file descriptor is already closed during a resize
race with process exit, Elwood should treat that resize as a no-op and rely on
the normal exit event to update lifecycle status. Other native PTY resize errors
must still surface.
- `status`: session lifecycle/status changes.
- `warning`: typed non-fatal adapter or environment issues observed during the
  session, such as Codex MCP startup warnings.
- `loop`: adapter-neutral recurring-loop lifecycle and failure events (§5.9).
- `activity`: adapter-neutral live events for common observability, including
  lifecycle changes, user messages, assistant messages, turn failures, reasoning, tool calls,
  tool results, web search, notifications, warnings, startup prompt automation,
  attention (blocked-on-a-human-decision) transitions, generic hooks, hook
  results, and hook errors.
- `hook`: every Claude hook event after parsing and validation.
- `dialog`: verified Claude and Codex workspace trust lifecycle events, and
  Codex update offers that Elwood does not skip ([§5.13](5.13-dialogs.md)).
- `codex:transcript`: live, best-effort Codex transcript observations for
  activity that Codex does not expose as hook events.
- `hookError`: hook bridge or parent-handler errors that failed open.

`activity` is the preferred event for parent apps that want a simple unified
"send message, observe what happened, send another message" loop across
adapters. Every activity event includes:

- `elwoodSessionId`
- `agent`: `claude` or `codex`
- `source`: `hook`, `transcript`, `terminal`, or `lifecycle`
- `kind`: normalized event kind
- `label`: short display label
- optional `text`
- optional normalized metadata fields:
  - `hookEventName`
  - `turnId`
  - `final`: `true` on an `assistant_message` with native evidence of final reply text
  - `toolName`
  - `toolUseId`
  - `toolInput`: the tool call's input arguments, serialized to a string
    (already-string inputs pass through; structured inputs are JSON-stringified),
    present on `tool_call` activity when the source exposes it.
  - `toolOutput`: the tool result's output, serialized to a string with the same
    rules, present on `tool_result` activity when the source exposes it.
  - `status`
  - `exitCode`
  - `failedOpen`
  - `transcriptPath`
  - `tokenUsage`, `rateLimits`, and `subagent` for native dashboard observations (§5.12)
- optional `raw` in-memory source payload

`raw` is live-only but intentionally not redacted. Parent applications that
subscribe to activity events should treat `raw` as potentially containing user
prompts, tool inputs, tool outputs, and hook payload details.

Parent apps should not need `raw` for common timeline rendering. Elwood MUST
populate the normalized metadata fields whenever those values are present in the
source hook, transcript item, or lifecycle event. Adapter-specific `raw` remains
available for deep debugging and unsupported future payloads.

A `turn_failure` activity reports an authoritative harness failure. Its
`turnFailure` has `category`, bounded `message`, and `disposition`. The
message uses the existing diagnostic and fallback rules for
[Claude §6.1](../06-claude-hook-bridge.md#61-required-hook-coverage) and
[Codex §5.8](5.8-session-api.md), which bound individual diagnostic fields to
2,000 UTF-16 code units plus an ellipsis. The categories are
`quota_or_credit`, `rate_limited`, `usage_limit`,
`model_unavailable`, `authentication`, `network_or_api`, `context_too_long`,
and `unknown`. For a usage limit, `resetsAtUnixSeconds` is present only when
the same structured diagnostic supplies a nonnegative safe integer
`error.resets_at` in Unix seconds. Elwood checks recognized structured
`error.code`, then `error.type`, then the adapter's native code. It uses
`unknown` when no code establishes a category. Classification reads the original
diagnostic within the adapter's existing ingress limits, independently of
display truncation. The diagnostic can contain a JSON-encoded service envelope
or a decoded envelope supplied by the hook. Elwood never classifies assistant
prose or terminal text.

Codex CLI 0.171.0 and 0.172.0 use `usage_limit_exceeded` for usage limits,
workspace credit depletion, and the service's `insufficient_quota`. When a
committed failed task supplies that native code with either exact Codex
workspace-credit-depletion diagnostic, or with Codex's exact quota diagnostic
`Quota exceeded. Check your plan and billing details.`, Elwood classifies it
as `quota_or_credit` and preserves the original message. Other messages with
that code remain subject to the usual classification.

A Codex `codex_error_info` kind with fields can record the last HTTP status
as `http_status_code`. When that status is the number 402 (Payment Required),
Elwood uses `insufficient_quota` as the failure's native code, so it is
`quota_or_credit`. When it is the number 429 (Too Many Requests), Elwood uses
`rate_limit_exceeded`, so it is `rate_limited`. A recognized structured
`error.code` or `error.type` in the diagnostic still comes first. Codex 0.171.0
and 0.172.0 record a 402 as `http_connection_failed` with status 402, and an
exhausted rate-limit retry as `response_too_many_failed_attempts` with status
429. Any other status, and a kind without one such as `internal_server_error`,
keeps the kind's usual category. Elwood reads the status only from that field,
never from the message.

| `rate_limited` | `rate_limit`, `rate_limit_error`, `rate_limit_exceeded` |
| `usage_limit` | `usage_limit_exceeded`, `usage_limit_reached` |

| `context_too_long` | `context_length_exceeded`, `context_window_exceeded`, `prompt_too_long` |

Claude sources this activity from `StopFailure` with its native prompt ID
when available. Codex sources it from a committed failed `task_complete`
with its native turn ID. The activity follows the corresponding raw event
and its existing activity, preserves their original ordering, and has a
`label` matching its category. These sources report terminal failures, so
the current activity's disposition is `final`. Retry reporting would require
a separate, explicit native source correlated to the turn. Elwood does not
infer retries from status or text.
The failure is delivered before any ready transition made on or following
that observed boundary. A rendered ready notification can precede evidence
that the harness has not yet delivered. Late failures remain tagged with
their original turn ID when the native evidence supplies one. They do not change
the current session status. During live Codex polling, Elwood contains rejected
native Promises returned by failure-activity listeners and reports them through
the existing once-per-channel transcript listener warning (§5.7). The native
reaction-attachment conditions in §6.4 apply. The emitter retains diagnostics
for up to 1,024 pending observer registrations. An evicted registration's
rejection is still contained, with no warning for that rejection.
Hook-triggered observation retains the hook diagnostic boundary.

A live main-conversation Claude API error that reports an exhausted quota
emits a typed `warning` with code `usage_limit_reached`, agent `claude`, and
source `transcript`. Elwood requires a committed synthetic assistant error
marked `isApiErrorMessage: true`, `apiError: "usage_limit_reached"`, and
`apiErrorParams.rate_limit_info.status: "rejected"`. The warning carries the
first nonblank native assistant diagnostic as `message`, trimmed and shortened
to its first 2,000 UTF-16 code units plus `…` when longer. It carries the
transcript path and native turn identity when available, an optional
`limitName` from the native limit heading of up to 64 ASCII characters,
an optional `nativeLimitType` of up to 64 lowercase ASCII letters, digits,
or underscores, and an optional `resetsAtUnixSeconds` from a nonnegative
safe integer native reset. The
warning activity exposes `text`, `transcriptPath`, and the optional `turnId`
and carries the full warning in `raw`. Historical backfill, the prefix
reread after a detected transcript rewind, subagent records, ordinary prose,
and generic rate-limit errors do not establish this observation. A qualifying forward record reports its limit once
as it is read, independently of a `StopFailure` hook. The warning does not
change input readiness or make a statement about other models' availability.

A live Codex `token_count` snapshot with an explicit recognized
`rate_limit_reached_type` emits the same `usage_limit_reached` warning with
agent `codex` and source `transcript`. Its `nativeLimitType` is one of
`rate_limit_reached`, `workspace_owner_credits_depleted`,
`workspace_member_credits_depleted`, `workspace_owner_usage_limit_reached`,
or `workspace_member_usage_limit_reached`. It carries the transcript path,
optional native limit ID and name, and each supplied window reset separately
in Unix seconds. Displayed IDs and names are nonblank strings at most 256
UTF-16 code units. Resets must be nonnegative safe integers. The warning's
`raw` string is the native reason. Its normalized activity carries the
entire warning in `raw`. Codex does not identify the blocking window or turn in a
snapshot. The warning uses an Elwood description of the native type. The
separate `turn_failure` retains the harness's diagnostic when a committed
failure supplies it. A repeated unchanged rejection is suppressed until
the latest rejection changes or a native `null` for the same nonblank native
limit ID clears duplicate suppression. This does not infer quota recovery. A usage percentage alone cannot establish a
rejection. Startup history and the prefix reread after a detected transcript
rewind do not emit quota warnings.
The warning does not change readiness.

A `user_message` requires a known native prompt with at least one character
outside Unicode White_Space. Validated textless submissions remain observable
via `UserPromptSubmit` hooks and as `hook` activity on both adapters.
Each hook with nonblank prompt text yields its own `user_message`, even when its
native prompt ID repeats an earlier submission's, unless it repeats a prompt
already shown in one of the two ways below. Claude Code 2.1.332 fires the hook
for a message queued during a running turn, such as `sendGuidance`, with the
running turn's prompt ID. The Claude adapter suppresses a nonblank hook in two
cases:

- Transcript recovery already showed the same prompt ID with the same exact
  native text, so a submission seen through both its record and its hook yields
  one message.
- The hook has a prompt ID not yet shown and the same exact text as a message
  still queued under a reused ID. Claude fires this second hook when an
  interrupt cancels a queued message's first hook before Claude finishes
  screening it, and then runs the message as its own turn.

A queued message stops being pending when such a hook claims it, or when the
transcript shows it delivered: a `queue-operation` record with
`operation: "remove"` and that text, or a user record with
`promptSource: "queued"` and that text. At most 64 queued messages stay pending.
None stay pending without transcript correlation or after a transcript rewind,
whose replayed records cannot tell old delivery from new, so a re-screened
message can then appear twice. Transcript recovery for a textless hook still requires a
prompt ID that has not been shown, except that a textless submission still
waiting for its record keeps it when a queued message reuses its ID.

A Claude or Codex text submission made through `sendMessage`, `sendPrompt`, or
`sendGuidance` may supply `SendOptions.sendId`, an opaque caller string of up to
1,024 UTF-16 code units. Invalid values are ignored. When a matching
`UserPromptSubmit` is uniquely established, its `user_message` carries the
original API `text`, `nativePrompt` with the unchanged hook text, any valid ID, and
`promptProvenance: { origin: "api", input: "pasted" }`. Activity without sufficient
evidence retains its existing fields. The ID stays inside Elwood. Submission
resolution and raw hook payloads remain unchanged.

The association supports image-free text submissions of up to
65,536 UTF-16 code units on a fresh session with an observably empty composer.
Elwood requires successful forwarding of the owned paste and an Enter, and a
new native turn whose nonblank hook prompt matches the forwarded text.
Codex compares line endings and Unicode White_Space trimming. Claude requires a
native `prompt_id` and compares the recognized standalone paste body or the
unwrapped prompt using the composer normalization in C-CLAUDE-25. Claude's
canonical comparison is also bounded to 65,536 UTF-16 code units. Claude
association is available on the low-level text APIs; its ergonomic
`send()` and `stream()` keep their existing prompt activity. Starting another paste
or command while an earlier forwarded paste remains unresolved makes association
unavailable for the session. Caller terminal input and unverified composer
ownership can also end tracking. A cancelled paste can regain eligibility after
owned cleanup confirms the composer is empty. An existing native turn ID cannot
identify a second submission, including guidance that stays in the same turn.
Caller IDs can repeat. Elwood remembers at most 1,024 native turn IDs of up to
128 UTF-16 code units. An invalid native ID or exhausted history ends tracking
because later unique attribution cannot be verified.

When API association is unavailable, Claude `user_message` activity removes a supported standalone native
`pasted_content` envelope from its displayed `text`. The opening line is
`<pasted_content id="hhhh">` and the closing line is
`</pasted_content id="hhhh">`. In both tags, `hhhh` is the first four lowercase
SHA-256 hex digits of the native session ID from the authenticated
`UserPromptSubmit` hook. LF separates each tag from the body. Up to two LFs can
precede the opening tag and up to two can follow the closing tag. The body must
contain nonblank text. A literal `<`, zero or more characters other than ASCII
letters, digits, underscore, backslash, angle brackets, and hyphen, then
case-insensitive `pasted_content` or `pasted-content` makes the body ambiguous
if the name ends there or the next character is outside `[A-Za-z0-9_-]`. Literal backslash escapes stay in the displayed body.
Elwood also applies this check to an eligible textless recovery whose content
is a single string or text block. When API association is unavailable, a normalized event carries
`promptProvenance: { origin: "unknown", input: "pasted" }` and `nativePrompt`, the
exact native prompt text including the envelope. The hook payload is unchanged.
Mixed, malformed, foreign, and unsupported input keeps its existing text and
omits paste metadata. This evidence describes Claude's native representation.
Exact original pasted text can be unavailable because Claude transforms line
endings, tabs, tag escapes, and trailing newlines before delivery.

For a textless Claude submission with a native prompt ID and absolute transcript
path, Elwood also emits `user_message` if forward transcript observation finds
nonblank text in a complete, non-metadata user record with the same native
prompt ID and path. Live recovery excludes any record containing a `tool_result`
block. The first authenticated textless hook can also recover the newest
eligible newline-terminated user record from the initial 1 MiB transcript tail,
searching at most 4,096 committed rows. The file must still match the identity,
size and timestamps recorded when Elwood began watching the authenticated path. The
lookup selects the newest eligible row before comparing its native prompt ID
to the authenticated hook. A mismatch spends the lookup for that path, without
searching older rows. The open descriptor and authenticated pathname must still
identify that version after the scan. An absent file at registration has no
initial evidence. Changed files keep ordinary forward observation. A transient read error permits
one retry while the same authenticated submission remains pending. A subsequent
scan can use the retry without another hook. Retirement or eviction clears its
authority.
The scan stops at the newest eligible row. Within the examined rows, an invalid
UTF-8 or JSON row containing the quoted token `"user"` or a backslash contributes
to one content-free `unparseable` notice per lookup.

A transcript recovery is observational and does not
acknowledge an API submission. Elwood emits at most one matching message within
its bounded live prompt evidence window. The window retains up to 64 unpaired
native prompt identities, up to 4 MiB of retained prompt text, and the most
recent 64 emitted prompt identities. Retirement clears unpaired evidence for
that path after its final drain. Recovered activity contains the normalized
text and identity without attaching the raw transcript record.

During Claude live polling, a listener failure on recovered prompt activity
emits one content-free `claude_prompt_listener_error` warning per watcher.
It has `agent: "claude"`, `source: "terminal"`, `severity: "warning"`, and
`channel: "activity"`. During a hook transaction, the hook observer diagnostic
takes precedence. A synchronous final-flush failure is reported before
`terminal:exit`. A rejection observed after final transcript delivery is
contained without emitting another event after exit.

Claude activity exposes the native prompt identity as `turnId`: `prompt_id` in
hooks and `promptId` in user transcript records identify the same turn. Empty
`prompt_id` values do not provide a turn identity. Committed
assistant, reasoning, and tool activity inherits that identity through the
transcript's `uuid`/`parentUuid` chain. The identity survives a `ready` transition
and a successor submission, so a delayed final message still names its original
turn. `status` changes alone do not create turns. Sources without a native prompt
identity retain the optional field rather than inventing a boundary from timing.
A first hook may identify a user prompt already baselined at EOF. Elwood may
retain that specific user record's UUID only when the bounded backward baseline
scan finds a genuine user prompt with the same native `promptId`; a pure
`tool_result` record is not a prompt boundary. An unknown parent is never
assigned the hook's identity.
Identity retention is bounded to the most recent 4096 record UUIDs per watched
transcript, 1024 UTF-8 bytes per UUID or prompt identifier, 4096 UTF-8 bytes per
retained path, 128 retained paths, and 1 MiB of aggregate retained path, UUID and
prompt-identifier bytes per watcher. Each UUID mapping charges both its UUID and
prompt identifier; count eviction happens before aggregate admission. Retirement
releases a path's identity evidence and its charged bytes. Exceeding an identifier,
path-count, path-byte or aggregate-byte limit clears all retained identity
evidence and disables transcript turn correlation for that watcher's remaining
lifetime. Activity continues without `turnId`. If a parent link is absent or
falls outside retained evidence, `turnId` is omitted rather than assigned to the
current turn.

`ready` describes the session's ability to take input. It can arrive before the
transcript watcher delivers the final reply. To identify final reply text, use
`assistant_message` with `final: true` and correlate using `turnId` when available.
Claude uses the committed main-conversation assistant record's native
`message.stop_reason: "end_turn"`. If the record contains multiple text blocks,
only the last emitted text block carries `final`. Synthetic records, sidechain
records, and files identified by a native hook as subagent transcripts do not
carry the marker. Codex uses a committed assistant message with
explicit `phase: "final_answer"` and text. Array-form Codex text is joined before
emitting the message as usual. When native final evidence is absent, `final` is
omitted and finality is unknown. A marker describes reply text in the native
record and does not certify completion of hooks or a turn. Transcript activity
continues as each record is observed, independently of session status.

Claude's exact `No response requested.` assistant placeholder is excluded when
the committed message identifies its model as `<synthetic>`. An ordinary model
reply containing the same words remains assistant activity.

Codex tool-result `text` and `toolOutput` include every textual output block.
For the native exec array envelope beginning with `Script completed`, an optional
wall-time line, and `Output:`, the envelope is omitted and the following blocks
are the result.
Inner output is retained verbatim, including text that itself says
`Script completed`. Plain-string results retain their original text.

Codex assistant messages with explicit `phase: "commentary"` in committed
`response_item` message records produce `kind: "assistant_progress"`,
`label: "assistant"`, and untruncated normalized `text`. String content and
array-form `output_text` blocks are supported; array text is concatenated in
order. Analysis/unknown phases and non-output-text blocks are excluded from this
user-facing channel. Final-answer and legacy unphased assistant messages retain
their `assistant_message` behavior. Progress carries the usual session identity,
transcript path, optional native turn ID, and raw source item.

Response items are the canonical source of commentary. Legacy `agent_message`
records with an explicit non-final phase remain raw transcript observations
with an `other` summary/activity and no normalized text; their mirror must not
publish a second progress message or a premature final answer. Unphased and
`final_answer` legacy agent messages retain existing behavior.

Progress is observational: it does not change status, indicate a turn boundary,
or enter ergonomic `send()` results or `stream()` text events. Consumers render
it in chronological order while retaining working state, reply context and trace
ownership until a final reply or native lifecycle boundary. Consumers must not
treat progress mentions as reply-routing instructions.

When Elwood detects and answers an interactive startup prompt on behalf of the
parent app, it MUST emit an activity event with `source: "terminal"`,
`kind: "startup_prompt"`, a stable label, and text describing the key sent. This
`startup_prompt` activity is emitted only after the prompt's PTY write actually
fulfills; a rejected write emits no such activity and instead surfaces the
`startup_prompt_write_failed` warning (§5.7) while leaving the prompt retryable
within the live session. The Claude auto-mode setup decline waits further, for a
settled frame without the offer's menu, and retries a rejected write within the offer's
appearance instead of on a later frame (C-CLAUDE-27). Claude browser-tools and
auto-mode decline disposal is a silent, permanent cancellation: pending writes
produce neither activity nor a write-failure warning, and no later frame retries
the decline (C-CLAUDE-22).

`auto_mode_setup` names the first menu of Claude's auto-mode setup offer, the

The trust-prompt labels (`workspace_trust`, `skill_trust`, `plugin_trust`,
`mcp_trust`, `bypass_permissions`, `hook_trust`) are exactly the ids in the
trust-prompt allowlist; a second implementation MUST treat this table as the
complete output union.

Under a caller's full-trust launch (`autotrust`), Elwood MUST attempt to approve
every safely recognized allowlisted trust gate. The family covers workspace,
skill, plugin, MCP, and Claude bypass-permissions acceptance (§5.1). This is an
EXPLICIT ALLOWLIST: automatic input requires a native header, recognized
explanatory/path rows, and an exact affirmative choice in the same active,
bottom-most dialog. Transcript content, quoted instructions, earlier headers,
unknown intervening prose, and unrelated options MUST NOT authorize input.
Wrapped native copy and partial rendering remain supported. Where a prompt's
native dialog carries explanatory copy (Claude workspace, MCP server, and
bypass-permissions, Codex directory and hooks), that copy is REQUIRED: a bare
allowlisted header with affirmative options is only a candidate, held and never
typed into, until its native body paints. Prompts with no known native body
(skill, plugin) are recognized from their header and native option rows.
Claude's prompt for one new project MCP server, `New MCP server found in this
project: <name>`, carries `MCP servers may execute code or access system
resources. All tool calls require approval. Learn more in the MCP documentation.`
and ends in `Enter to confirm · Esc to reject`; its affirmative choice is `Use
this MCP server`. Claude's prompt for several new servers at once is a checklist,
not on the allowlist, and is never answered.

Claude 2.1.326 and later add a load row to the workspace prompt, after `Claude
Code'll be able to read, edit, and execute files here.`: `Trusting this folder
loads <items>.` Elwood takes its grammar from the 2.1.332 binary and has
confirmed it with captures on 2.1.329 and 2.1.332. Its items are, in this order,
each project settings file that exists and parses, `.claude/settings.json` then `.claude/settings.local.json`,
then `.mcp.json here or above (MCP servers)` when an `.mcp.json` in the folder or
above it declares MCP servers. A settings file whose hooks, status line command,
or helpers run commands is followed by ` (runs commands)`. Items join as Claude
joins lists: one alone, two with ` and `, three as `<a>, <b>, and <c>`. When a
settings file runs commands, Claude 2.1.329 and later put `⚠ This folder
configures hooks that can run commands without asking, declared in <files>` before
the load row, where `<files>` names exactly the files marked ` (runs commands)`,
joined the same way. When a settings file's `permissions.allow` lists rules,
Claude 2.1.329 and later put a permissions warning before the hooks warning, or
before the load row when there is none: `⚠ This folder pre-approves <N> tool
permission[s] in <files>:`, with the singular noun for a count of 1 and the plural
otherwise, where `<files>` names settings files the load row names, joined the
same way; then the rules themselves, which the folder chooses, on one or more
rows; then `These will apply without asking. Only proceed if you trust this
configuration.` on its own row. Elwood reads the rules as opaque text and never
derives anything from them: only the rows around them are checked, and a rule may
not contain `⚠`. The closing sentence must be that whole row, followed by a blank
row or a warning, which no rule can draw, so a rule that quotes it never
stands in for it. Claude closes up to three warnings with that one sentence: the
permissions warning, then warnings that the folder adds workspace directories or
runs a headers helper. Only the permissions warning is recognized, so any warning
between the rules and the closing sentence fails closed. The permissions warning
around its rules, the hooks warning, and the load row, exactly, in that order,
wrapped or not, belong to the recognized workspace copy, and a caller's
`autotrust: true` approves the prompt like the plain one; approving it also
applies the pre-approved permissions. Claude then loads what they name: it
runs the folder's hooks, it applies the settings files, which can enable plugins
whose hooks run without a further prompt, and it offers new MCP servers (above).
For one server it draws the MCP server prompt, which a caller's `autotrust: true`
answers with `Use this MCP server`. For several at once it draws a checklist,
which Elwood never answers. The automatic trust a model probe implies does not
approve a prompt with a load row (§5.3). A file marked ` (runs commands)` that
the hooks warning does not name, the hooks warning without its load row, another
annotation such as ` (sets environment variables)`, another warning, or any other
prose in the dialog still fails closed. Claude 2.1.326 through 2.1.328 draw the
load row without the hooks warning, so their prompt for a folder whose settings
run commands fails closed.

A known native-header candidate immediately holds initial readiness and queued
input, even when its copy/options are incomplete or unsupported. Candidate
recognition is only authority to hold input, never authority to approve. One
session-owned coordinator gives each observed dialog generation its own
reservation and bounded five-second deadline, beginning at first candidate
observation. Partial first paints receive that interval without an immediate
`blocked` transition. Numbered and cursor layouts share the same safety checks:
before every number, selection, confirmation, and retry, the session must still
be live and the same generation, native header, and exact affirmative choice must
remain valid. Cursor selection movement and completion of native option rows do not
alone replace a generation. Clearing and reappearance do. An older completion
cannot release or settle a newer generation's reservation.

A numbered answer's first write types its number. A frame that still shows the
gate does not prove the CLI ignored that write: under load a CLI can take it and
paint its next screen after the retry interval, and the number typed again would
be submitted from its composer as a user message. Retries therefore never type
the number on that evidence alone. Codex's answer retries, at bounded intervals,
as Enter alone while the rendered caret is on the affirmative: on the gate Enter confirms that option, and
on Codex's empty composer it submits nothing. Otherwise (any Claude layout, or a
caret on another option) the number is typed again only after a frame rendered
from output received after the last write still shows the gate. Once Elwood has
started writing a gate's number, every later attempt at that gate retries the
same way, even when that write or a retry was rejected (a rejected write may
still have reached the CLI), until another complete dialog replaces the gate and
the CLI draws it afresh. A cursor layout never receives a relative arrow or a bare
Enter: Elwood selects the affirmative by its absolute row (Home, then one Down
per option above it), repeats that selection while the rendered cursor is
elsewhere, and sends Enter only in the same write as the selection, once the
rendered cursor is on the affirmative. A delayed, duplicated, or lost key, or a
CLI that resets its own selection after Elwood read the frame, therefore cannot
confirm another option.
Raw input through `sendKeys`, `terminal.sendInput`, or `xterm.input` while a
trust dialog generation is on screen hands that generation to the caller. Its
attempt is cancelled before the caller's keys are written, and Elwood writes
nothing more to it, even if it repaints or outlives its five-second deadline
(it then falls back to `blocked` as below). The frame Elwood reads can trail
the CLI, so a retry typed after the caller's keys could land in the composer
and submit them. A later dialog generation is answered as usual. The same raw
input ends a running Codex update-skip attempt before the caller's keys are
written, so none of its retries follow them. A Codex update prompt that is on
screen, or that left the screen without positive native composer clearance,
then belongs to the caller: Elwood writes no skip to it, even when its frame
loses and regains the prompt, until positive native composer clearance. An
update prompt appearing after that clearance is handled as usual.
An unambiguous changed versioned Codex update banner, a bannered replacement with
changed or removed safe-option bindings and a valid safe choice, or a fresh unambiguous
banner with a valid current safe choice after update eligibility was revoked,
emits terminal `attention` labelled
`codex-update-prompt` with an optional numeric `promptGeneration`. This generation
is monotonically increasing within the live session. Fresh evidence may repeat the
same version pair after revocation; ordinary redraws, bannerless choices, and
ambiguous frames cannot renew it. After revocation, banner-only and action-only
repaints cannot reauthorize old bannerless choices or renew grace. It renews the CLI's bounded update grace once;
duplicate or older generation signals cannot extend that grace. It does not claim
that a key was written or that the prompt was answered.

With a live frame reader, `startup_prompt` is emitted only after a fulfilled
confirmation and a verified native composer or distinct native successor gate.
An unknown replacement is not successful clearance. Nor does a frame without the
gate end a fulfilled confirmation: once the confirming write fulfills, blank,
banner-only, or other dialog-free frames (the CLI erased the answered dialog and
is painting its next screen) neither settle nor cancel the attempt, which writes
nothing while the gate is absent. Later verified clearance reports it exactly
once; the same gate's return resumes answering within its remaining budget; a
changed gate, a complete off-allowlist gate (C-ATTN-03), expiry, and closing
cancel it without a report.
Lost revalidation before the confirmation fulfills cancels that attempt quietly,
retaining input ownership while clearance is unverified.
Stop, kill, teardown, startup cleanup, and PTY exit cancel all trust attempts and
timers before disposal; late completions emit neither success nor warnings.
Only an actual rejected PTY write in a still-live matching attempt produces the
content-free `startup_prompt_write_failed` warning.

If automation cannot safely clear the gate within five seconds, the live session
MUST enter recoverable `blocked` status and emit the existing human `attention`
activity, even without another terminal frame. Those five seconds count only time
the gate is on the current rendered frame. A frame without it — the CLI erased an
answered dialog and is still painting its next screen — pauses the deadline, and
the same gate's return resumes the remainder rather than a fresh interval, so the
budget is five seconds of cumulative visible time. A gate that leaves the frame
before those five seconds are spent and stays absent until verified clearance
therefore never produces `blocked` or `attention`, however long the CLI then
takes to paint its composer: no prompt is left for a human to answer. A gate that
returns spends only what remains and falls back once its visible time reaches
five seconds. Its input hold is unchanged and lasts until verified clearance. Unsupported
layouts and exhausted attempts use this same fallback; they never cause blind
input or false write warnings. An unchanged redraw cannot restart an expired
attempt indefinitely.
During Codex startup, raw input on the last settled native prelude gives the
caller control of the first matching workspace trust question. Queued native
output alone leaves that prelude eligible for raw caller input.
`Folder access` pairs with `Trust this folder?`. A legacy `> You are in <absolute path>`
row pairs with `Do you trust the contents of this directory?`. These preludes
must appear outside conversation content. Elwood withholds automatic input for
the claimed question even while its choices are still appearing. A settled
incompatible frame, loss of native render provenance, or verified startup
readiness ends eligibility and clears any pending prelude claim.

A newly valid layout or a new dialog generation re-arms bounded safe automation;
once fallback has occurred, the public block remains until verified clearance.
Raw `sendKeys` remains available for human recovery, while queued persona,
message, and command input remains held. Headless CLI callers report the existing
`blocked_prompt` failure. No new public status, warning, or activity shape is added.

Normally successful automation MUST NOT produce a `blocked` transition. A
recognized prompt whose affirmative is still painting may retain its once-per-
generation transient `attention` labelled with the prompt id; it is distinct
from the fallback attention's blocking rule id. A candidate whose native body has
not validated emits no transient `attention`. With `autotrust` off, an
unanswered trust candidate blocks immediately for the human. This hold survives
partial or unknown replacements until a verified native composer or a recognized
successor takes ownership; losing the header alone never reopens queued input.
All recognition
uses the current rendered frame, never accumulated history.

Both adapters MUST retain trust input ownership until all received terminal output
has rendered successfully. A staged tail, pending render, synchronized redraw, or
render failure cannot clear human trust or authorize a trust retry. Retry reads
that are temporarily unavailable wait within the existing attempt deadline;
they never reuse the previous frame or enter the no-reader compatibility path.

Live composer clearance requires a native input cursor on the verified composer
row. Codex uses the visible hardware cursor. Claude accepts either the visible
hardware cursor or a reverse-video space drawn at the empty input position while
the hardware cursor is hidden. The painted cell must belong to the fenced empty
composer at that cursor row. The rows below it may include native composer
footers and the recognized login-renewal notice (§5.7).
Claude uses the same cursor evidence for empty-input recovery. Cursor evidence, coordinates, title, and text must belong
to the same completed render. Output received but not yet rendered cannot prove
clearance. Transcript caret/option text and ordinary quoted working prose are not current
input controls merely because they resemble one. A missing input cursor or a
cursor outside the composer keeps caller input held through partial repaints.
Native approval headers at the dialog's leading column also retain the hold;
a still-visible cursor on an older composer cannot override that replacement
evidence. Indented transcript quotations are not native approval headers.
An exact-shaped native working row remains ambiguous even with a visible input
cursor: Codex permits typing while running, and its title spinner is configurable.
Such a row conservatively retains the hold, including an identical transcript quotation.

Claude's verified composer is the empty `❯` row between its two rules, plus native
chrome: the permission-mode footer as the very next row, or the `Claude Code v…`
version banner. The footer proves the composer in every permission mode the CLI
offers (manual, plan, accept edits, auto, don't ask, bypass permissions), with or
without vim's `-- INSERT --` prefix, the transient `← for agents` and `? for
shortcuts` hints, and the right-aligned token count or effort level. The banner
MUST NOT be required, because it scrolls out of the viewport in a long session.
Trust clearance, foreign model-picker release (C-API-55) and empty-input
observation (C-API-56) share this evidence. A footer quoted anywhere other than
directly under the composer's bottom rule is transcript, not chrome, and a footer
truncated on a narrow terminal does not prove the composer.

An unrecognized gate behind a recognized native header prefix is hold-only
under every `autotrust` value. The recognized prefixes are exactly the
line-leading `Do you`, `Quick safety`, `Is this`, `Load this`, `Trust the`, `Trust this`,
`New MCP`, `WARNING:`, `Claude Code running`, and `Hooks need` (the adapter's
`headerStart`). When the bottom-most such region has non-empty header text,
selectable options, nothing below them but option rows and the native footer
that ends the frame (`Enter to confirm`/`Esc to cancel`, or `Press enter to
continue|confirm or esc to cancel|go back`, or `enter continue · esc quit`), no
conversation row above it, and no region names an allowlisted prompt, it MUST hold
readiness and queued input, MUST NOT receive any automated keypress (trust answers,
the Codex update skip and its retries, or the Claude browser-tools decline), and
blocks for the human
with the attention rule id `<agent>-unknown_gate-prompt`. A dialog that another blocking
rule already names (a tool permission or approval dialog) keeps that rule's
label alone. The hold follows the current frame: it releases once that gate is
no longer rendered, and raw `sendKeys` remains available to answer it. While
ANY trust candidate is rendered — this gate or an allowlisted header, even a
hold-only one with unsupported copy — the Codex update skip (first write and
every retry) and the Claude browser-tools decline MUST NOT write. This is
NOT a general guarantee: a gate whose header starts with any other words, whose
footer is not yet painted or not one of those rows, or that carries other rows
below its options is outside this grammar and is not held.

Codex 0.164 draws two more footers when hook trust is not bypassed:
`enter continue · esc back` on its folder-access gate, whose decline then reads
`Back to Agent Command Center`, and `enter confirm · esc skip` on `Hooks need review`.
Neither is one of the rows above. Each ends a dialog only under the allowlisted gate
that draws it, with that gate's header, explanation, and options, so under any other
header or options, including conversation text, it makes no frame a trust gate.
Claude's MCP server prompt's footer, `Enter to confirm · Esc to reject`, is bound to

Two prompts are exceptions to the `autotrust` gate. Codex hook trust
(`hook_trust`) is always enabled because the session requires its hook bridge.
Codex's hook-trust bypass is session-wide: it trusts ALL configured hooks,
including third-party hooks, independently of `autotrust`. `update` is not a
trust decision at all and is also handled independently of `autotrust`.
Every hook dispatch must also emit an adapter-neutral hook-result activity after
parent handlers run. The result activity must include the hook event name,
whether the dispatch failed open, and the raw in-memory result payload when
present. Missing parent handlers are normal no-decision responses and must not
be labeled as failed-open errors. Handler timeouts, invalid responses, thrown
handlers, and bridge errors must emit both `hookError` and an adapter-neutral `activity` with
`kind: "hook_error"`.

`HookErrorEvent.category` values are `timeout`, `handler_error`,
`invalid_input`, `invalid_response`, and `bridge_error`.

Hook-specific events remain the source of truth for event-specific decisions,
typed control responses, and adapter-specific payloads.

for the first observed failure. Its message and raw diagnostic contain only fixed

### Unrecognized agent startup screen

Before a session's first readiness, once its readiness deadline (10 seconds after
the first rendered frame, §5.3) has passed, a completed live frame is an
unrecognized startup screen when it has visible text and shows none of these:

- the adapter's configured composer (§5.3);
- a recognized blocking dialog or trust prompt;
- startup automation in progress: a trust answer, or Codex's update-skip repaint;
- visible work;
- a boot frame: the agent's own header, Claude's `Claude Code v<version>` banner or
  Codex's `>_ OpenAI Codex (v<version>)` header, with no other row a person could
  answer, as the CLI draws while it loads. An answerable row has a caret before text
  or a prompt ending in a caret, a numbered choice, a `(y/n)` question, or a key hint
  phrased as `Enter to`, `Esc to`, `Tab to`, `Press <key>`, or `to continue`,
  `to confirm` or `to cancel`. A bare caret, as Codex paints before its placeholder,
  is not answerable;
- Codex's boot composer or its `Resuming session…` placeholder;
- Codex's composer with its status footer while readiness waits for the footer to show
  the requested effort (§5.3).

A completed frame is one whose output has all rendered and that no later output has
changed. At the deadline Elwood classifies the terminal's current settled screen,
which a resize can have reflowed without the agent repainting it. While output is
still rendering, the next completed frame is classified instead.

Elwood blocks the session on such a screen as it does on a recognized dialog. The
status becomes `blocked`, and Elwood emits terminal `attention` labelled
`claude-unrecognized-startup` or `codex-unrecognized-startup`. Readiness, queued
input and every operation that writes to the terminal wait, except raw caller
input (C-ATTN-11). With the block Elwood emits terminal activity with
`kind: "unrecognized_startup"`, `label: "initial_ready_deadline"`, and `text`
holding that frame, bounded as below. A status or attention listener that throws
does not prevent this activity, and a listener that throws on this activity is a
frame observer failure (C-API-72). A run of consecutive unrecognized
frames reports once, so an animated screen reports once. A screen that follows a
recognized frame starts a new run and reports again.

The host answers the screen with raw `sendKeys` or `terminal.sendInput`, or stops
the session. The block ends as a recognized dialog's does (C-ATTN-02): on a
verified idle composer, where readiness then releases queued input, or with work
on screen. A readiness hook that arrives during the block waits for that composer,
as during a recognized dialog. A recognized dialog that replaces the screen keeps
the session `blocked` under its own label. A recognized frame that is neither,
such as Codex's boot composer after the answer, ends the run of unrecognized
frames but not the block. A blank or incomplete frame ends neither. After the first
readiness nothing is reported as an unrecognized startup screen.

If the Claude or Codex readiness backstop expires without a configured composer
or a recognized hold on startup readiness, Elwood also emits terminal activity with
`kind: "unrecognized_startup"`, `label: "initial_ready_backstop"`, and `text`
containing the last completed live screen. An unrecognized startup screen's own
block is not a recognized hold, on any frame within it. In both events Elwood
replaces each `sk-` API-key-shaped token, `sk-` that does not follow a letter, digit or `_`, then at
least eight key characters (letters, digits, `.`, `_` or `-`), with
`sk-[REDACTED]`, the marker Elwood's CLI output uses. A key can wrap. A row can
end in `sk-` and any letters, digits, `_` or `-`, or in only the `s` or `sk` of
that prefix, followed by nothing but optional spaces and an optional `│` border;
again the `s` does not follow a letter, digit or `_`. When the next row's
leading run of such characters, after optional spaces and an optional border,
completes `sk-` and one of them, the part ending the row becomes `sk-[REDACTED]`
and the run becomes `[REDACTED]`, even when it is an ordinary word. While a run
is all its row holds, apart from spaces and a border, the next row's leading run
becomes `[REDACTED]` too. A key the agent masked with dots, such as
`sk-ant-...Tail`, does not continue onto the next row. Rows without an `sk-`
start on the screen, such as the tail of a key whose start scrolled away, are
not recognized as a key. Elwood redacts before it removes trailing whitespace
and limits the text to its last 8,192 UTF-16 code units without splitting a
surrogate pair. The backstop event uses an empty string if no completed frame
contains visible text, and is emitted once per start. Both events are live-only
and carry no inferred choice or authority to write. Otherwise the text is whatever the
agent drew, which can include account or workspace details, or other credentials
the agent showed. `terminal:data` and its replay to late subscribers (C-PTY-03),
`terminal.snapshot()` (§5.3) and `readScreen()` (§5.14) carry the same screen
unredacted. The existing warning remains content-free, and queued input remains
held.
