## 5.4 Events

The primary event API is typed event-emitter style.

Required event families:

- `terminal:data`: raw PTY output bytes/string for live rendering.
- `terminal:exit`: PTY process exit.

`resize` should update both terminal models while the process is alive. If the
native PTY reports that its file descriptor is already closed during a resize
race with process exit, Elwood should treat that resize as a no-op and rely on
the normal exit event to update lifecycle status. Other native PTY resize errors
must still surface.
- `status`: session lifecycle/status changes.
- `warning`: typed non-fatal adapter or environment issues observed during the
  session, such as Codex MCP startup warnings.
- `loop`: adapter-neutral recurring-loop lifecycle and failure events (§5.9).
- `activity`: adapter-neutral live events for common observability, including
  lifecycle changes, user messages, assistant messages, reasoning, tool calls,
  tool results, web search, notifications, warnings, startup prompt automation,
  attention (blocked-on-a-human-decision) transitions, generic hooks, hook
  results, and hook errors.
- `hook`: every Claude hook event after parsing and validation.
- `codex:transcript`: live, best-effort Codex transcript observations for
  activity that Codex does not expose as hook events.
- `hookError`: hook bridge or parent-handler errors that failed open.

`activity` is the preferred event for parent apps that want a simple unified
"send message, observe what happened, send another message" loop across
adapters. Every activity event includes:

- `elwoodSessionId`
- `agent`: `claude` or `codex`
- `source`: `hook`, `transcript`, `terminal`, or `lifecycle`
- `kind`: normalized event kind
- `label`: short display label
- optional `text`
- optional normalized metadata fields:
  - `hookEventName`
  - `turnId`
  - `toolName`
  - `toolUseId`
  - `toolInput`: the tool call's input arguments, serialized to a string
    (already-string inputs pass through; structured inputs are JSON-stringified),
    present on `tool_call` activity when the source exposes it.
  - `toolOutput`: the tool result's output, serialized to a string with the same
    rules, present on `tool_result` activity when the source exposes it.
  - `status`
  - `exitCode`
  - `failedOpen`
  - `transcriptPath`
- optional `raw` in-memory source payload

`raw` is live-only but intentionally not redacted. Parent applications that
subscribe to activity events should treat `raw` as potentially containing user
prompts, tool inputs, tool outputs, and hook payload details.

Parent apps should not need `raw` for common timeline rendering. Elwood MUST
populate the normalized metadata fields whenever those values are present in the
source hook, transcript item, or lifecycle event. Adapter-specific `raw` remains
available for deep debugging and unsupported future payloads.

When Elwood detects and answers an interactive startup prompt on behalf of the
parent app, it MUST emit an activity event with `source: "terminal"`,
`kind: "startup_prompt"`, a stable label, and text describing the key sent. This
`startup_prompt` activity is emitted only after the prompt's PTY write actually
fulfills; a rejected write emits no such activity and instead surfaces the
`startup_prompt_write_failed` warning (§5.7) while leaving the prompt retryable
within the live session. Claude browser-tools disposal is a silent, permanent
cancellation: pending writes produce neither activity nor a write-failure warning,
and no later frame retries the decline (C-CLAUDE-22).
The stable startup-prompt label set is EXACTLY the following, and no other value
may be emitted with `kind: "startup_prompt"`:

| label             | agent          | defined by                  |
| ----------------- | -------------- | --------------------------- |
| `workspace_trust` | claude, codex  | C-CLAUDE-10, C-CODEX-11/15   |
| `skill_trust`     | claude         | C-CLAUDE-14                 |
| `plugin_trust`    | claude         | C-CLAUDE-14                 |
| `mcp_trust`       | claude         | C-CLAUDE-14                 |
| `bypass_permissions` | claude      | C-CLAUDE-21                 |
| `browser_tools`   | claude         | C-CLAUDE-11                 |
| `hook_trust`      | codex          | C-CODEX-06/15               |
| `update`          | codex          | C-CODEX-12                  |

The trust-prompt labels (`workspace_trust`, `skill_trust`, `plugin_trust`,
`mcp_trust`, `bypass_permissions`, `hook_trust`) are exactly the ids in the
trust-prompt allowlist; a second implementation MUST treat this table as the
complete output union.

Under a caller's full-trust launch (`autotrust`), Elwood MUST attempt to approve
every safely recognized allowlisted trust gate. The family covers workspace,
skill, plugin, MCP, and Claude bypass-permissions acceptance (§5.1). This is an
EXPLICIT ALLOWLIST: automatic input requires a native header, recognized
explanatory/path rows, and an exact affirmative choice in the same active,
bottom-most dialog. Transcript content, quoted instructions, earlier headers,
unknown intervening prose, and unrelated options MUST NOT authorize input.
Wrapped native copy and partial rendering remain supported. Where a prompt's
native dialog carries explanatory copy (Claude workspace and bypass-permissions,
Codex directory and hooks), that copy is REQUIRED: a bare allowlisted header with
affirmative options is only a candidate, held and never typed into, until its
native body paints. Prompts with no known native body (skill, plugin, MCP) are
recognized from their header and native option rows.

A known native-header candidate immediately holds initial readiness and queued
input, even when its copy/options are incomplete or unsupported. Candidate
recognition is only authority to hold input, never authority to approve. One
session-owned coordinator gives each observed dialog generation its own
reservation and bounded five-second deadline, beginning at first candidate
observation. Partial first paints receive that interval without an immediate
`blocked` transition. Numbered and cursor layouts share the same safety checks:
before every number, arrow, Enter, and retry, the session must still be live and
the same generation, native header, and exact affirmative choice must remain
valid. Cursor selection movement and completion of native option rows do not
alone replace a generation. Clearing and reappearance do. An older completion
cannot release or settle a newer generation's reservation.

Numbered confirmations retry at bounded intervals when the native input loop
has not consumed them; cursor navigation likewise waits for verified progress.
With a live frame reader, `startup_prompt` is emitted only after a fulfilled
confirmation and a verified native composer or distinct native successor gate.
An unknown replacement is not successful clearance. Lost revalidation cancels
that attempt quietly, retaining input ownership while clearance is unverified.
Stop, kill, teardown, startup cleanup, and PTY exit cancel all trust attempts and
timers before disposal; late completions emit neither success nor warnings.
Only an actual rejected PTY write in a still-live matching attempt produces the
content-free `startup_prompt_write_failed` warning.

If automation cannot safely clear the gate within five seconds, the live session
MUST enter recoverable `blocked` status and emit the existing human `attention`
activity, even without another terminal frame. Unsupported layouts and exhausted
attempts use this same fallback; they never cause blind input or false write
warnings. An unchanged redraw cannot restart an expired attempt indefinitely.
A newly valid layout or a new dialog generation re-arms bounded safe automation;
once fallback has occurred, the public block remains until verified clearance.
Raw `sendKeys` remains available for human recovery, while queued persona,
message, and command input remains held. Headless CLI callers report the existing
`blocked_prompt` failure. No new public status, warning, or activity shape is added.

Normally successful automation MUST NOT produce a `blocked` transition. A
recognized prompt whose affirmative is still painting may retain its once-per-
generation transient `attention` labelled with the prompt id; it is distinct
from the fallback attention's blocking rule id. A candidate whose native body has
not validated emits no transient `attention`. With `autotrust` off, an
unanswered trust candidate blocks immediately for the human. This hold survives
partial or unknown replacements until a verified native composer or a recognized
successor takes ownership; losing the header alone never reopens queued input.
All recognition
uses the current rendered frame, never accumulated history.

Both adapters MUST retain trust input ownership until all received terminal output
has rendered successfully. A staged tail, pending render, synchronized redraw, or
render failure cannot clear human trust or authorize a trust retry. Retry reads
that are temporarily unavailable wait within the existing attempt deadline;
they never reuse the previous frame or enter the no-reader compatibility path.

Live Claude and Codex composer clearance requires a visible native input cursor on the
verified composer row. Cursor visibility, coordinates, title, and text must belong
to the same completed render; output received but not yet rendered cannot prove
clearance. Transcript caret/option text and ordinary quoted working prose are not current
input controls merely because they resemble one. Native dialog cursor hiding or a
cursor outside the composer keeps caller input held through partial repaints.
Native approval headers at the dialog's leading column also retain the hold;
a still-visible cursor on an older composer cannot override that replacement
evidence. Indented transcript quotations are not native approval headers.
An exact-shaped native working row remains ambiguous even with a visible input
cursor: Codex permits typing while running, and its title spinner is configurable.
Such a row conservatively retains the hold, including an identical transcript quotation.

An unrecognized gate behind a recognized native header prefix is hold-only
under every `autotrust` value. The recognized prefixes are exactly the
line-leading `Do you`, `Quick safety`, `Is this`, `Load this`, `Trust the`,
`New MCP`, `WARNING:`, `Claude Code running`, and `Hooks need` (the adapter's
`headerStart`). When the bottom-most such region has non-empty header text,
selectable options, nothing below them but option rows and the native footer
that ends the frame (`Enter to confirm`/`Esc to cancel`, or `Press enter to
continue|confirm or esc to cancel|go back`), no conversation row above it, and
no region names an allowlisted prompt, it MUST hold readiness and queued input,
MUST NOT receive any automated keypress (trust answers, the Codex update skip
and its retries, or the Claude browser-tools decline), and blocks for the human
with the attention rule id `<agent>-unknown_gate-prompt`. A dialog that another blocking
rule already names (a tool permission or approval dialog) keeps that rule's
label alone. The hold follows the current frame: it releases once that gate is
no longer rendered, and raw `sendKeys` remains available to answer it. While
ANY trust candidate is rendered — this gate or an allowlisted header, even a
hold-only one with unsupported copy — the Codex update skip (first write and
every retry) and the Claude browser-tools decline MUST NOT write. This is
NOT a general guarantee: a gate whose header starts with any other words, whose
footer is not yet painted or not one of those rows, or that carries other rows
below its options is outside this grammar and is not held.

Two prompts are exceptions to the `autotrust` gate. Codex hook trust
(`hook_trust`) is always enabled because the session requires its hook bridge.
Codex's hook-trust bypass is session-wide: it trusts ALL configured hooks,
including third-party hooks, independently of `autotrust`. `update` is not a
trust decision at all and is also handled independently of `autotrust`.
Every hook dispatch must also emit an adapter-neutral hook-result activity after
parent handlers run. The result activity must include the hook event name,
whether the dispatch failed open, and the raw in-memory result payload when
present. Missing parent handlers are normal no-decision responses and must not
be labeled as failed-open errors. Handler timeouts, invalid responses, thrown
handlers, and bridge errors must emit both `hookError` and an adapter-neutral `activity` with
`kind: "hook_error"`.

`HookErrorEvent.category` values are `timeout`, `handler_error`,
`invalid_input`, `invalid_response`, and `bridge_error`.

Hook-specific events remain the source of truth for event-specific decisions,
typed control responses, and adapter-specific payloads.

Elwood may provide convenience registration by hook name:

```ts
session.on("hook:PreToolUse", async (event) => {
  return { permissionDecision: "deny", permissionDecisionReason: "No writes" };
});
```

The exact naming may vary, but the type system MUST narrow event payload and
valid response shape by hook event name.
