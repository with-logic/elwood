## 5.11 Native speed controls

Speed is adapter-specific. `StartCodexOptions` and `ResumeCodexOptions` expose
`serviceTier?: CodexServiceTier`, where `CodexServiceTier` is `"default" | "fast" |
"ultrafast"`. `StartClaudeOptions` and `ResumeClaudeOptions` expose
`fastMode?: boolean`. The lazy session constructors accept the same start options.
The `startOrResume` helpers forward these options on both paths.
The package root exports `codexServiceTierChoices`, the frozen readonly tuple
`["default", "fast", "ultrafast"]`, for hosts that display the setting. This
tuple describes launch values, while model rows supply availability hints.

Omitting a speed option inherits native configuration; it does not mean standard speed.
Explicit Codex `default` and Claude `false` request standard speed. Elwood validates
after launch-directory checks but before fresh-start state setup or preflight (and, on
resume, after identity checks but before reserving launch ownership or running
preflight), rejecting other values with `invalid_speed`, including an `agent`, `option`
and accepted `valid` values in error details. Typed speed options override a duplicate
raw `configOverrides`/`settingsOverrides` entry. No speed choice is persisted in
Elwood's session record or written to native user configuration. A host remembers its
preference and re-supplies it when resuming. Changes to a running conversation are
applied by stopping and resuming after the current turn; this API does not send native
toggle commands or interrupt a turn.

Resume also accepts the adapter's existing raw overrides, and `startOrResume`
forwards them. Omitted raw overrides are not recovered from a prior launch.
All other resume posture and identity guarantees remain unchanged.

### Evidence and availability

A requested option is not proof of eligibility or actual service speed. Models,
accounts, providers and managed settings can refuse a mode or fall back. Elwood
must not equate successful launch with confirmation that Fast or Ultrafast ran.

Codex model enumeration may include `codexServiceTiers: { fetchedAt, values }` on each
`AgentModelOption`, based on the native `models_cache.json` read beside THIS session's
resolved config file. When matching valid cache evidence is available, Elwood supplies
`default` as the baseline tier; recognized native cache entries provide additional
tiers. Native `priority` is normalized to `fast`. The `values` array is a nonempty
readonly tuple starting with the Elwood-supplied `default`, including for an explicitly
empty native tier array. Unknown future tiers are omitted. This is cached model
capability evidence, not a live account entitlement check. The timestamp is preserved.
Missing, unreadable, non-regular, oversized (>1 MiB), malformed or unmatched cache data
leaves the field absent (unknown), without breaking model enumeration. Only an explicit
native `service_tiers` array supplies this evidence. Claude enumeration does not invent
an availability list.

Only transcript activity can carry an optional `speed: AgentSpeedObservation`. The
public event type correlates its observation with the outer event's adapter:

- Codex: `{ agent: "codex", serviceTier, evidence: "turn_configuration" }` from
  an explicit `turn_context.payload.service_tier`. `priority` normalizes to
  `fast`. This confirms the turn's selected tier, not the provider's billed tier.
- Claude: `{ agent: "claude", fastMode, evidence: "response_usage" }` from
  an assistant message's `usage.speed` (`fast` or `standard`).

Absent, malformed or unknown values produce no observation, never a guessed
standard mode. Observations stay attached to the existing transcript path and
session identity; consumers must scope them to the intended primary/subagent
transcript. They describe that record, not a persistent account capability or
current setting after later changes. Elwood does not replay historical records to
fill this field on resume.
