## 5.5 Starting Codex

```ts
type StartCodexOptions = {
  readonly cwd: string;
  readonly env?: LaunchEnvironmentOverrides;
  readonly stateDir?: string;
  readonly initialSize?: TerminalSize;
  readonly hooks?: CodexHookHandlers;
  readonly persona?: string;
  readonly model?: string;
  readonly reasoningEffort?: CodexReasoningEffort;
  readonly serviceTier?: CodexServiceTier;
  readonly profile?: string;
  readonly sandbox?: "read-only" | "workspace-write" | "danger-full-access";
  readonly approvalPolicy?: "untrusted" | "on-request" | "never";
  readonly configOverrides?: readonly string[];
  readonly highTrust?: boolean;
  readonly autoupdate?: boolean;
  readonly autotrust?: boolean;
  readonly hookTimeoutMs?: number;
  readonly strictVersionCheck?: boolean;
};

type CodexReasoningEffort =
  | "none"
  | "minimal"
  | "low"
  | "medium"
  | "high"
  | "xhigh"
  | "max"
  | "ultra";

declare const codexReasoningEfforts: readonly [
  "none", "minimal", "low", "medium", "high", "xhigh", "max", "ultra"
];

declare function startCodex(options: StartCodexOptions): Promise<CodexSessionApi>;
```

`codexReasoningEfforts` is exported from the package entrypoint as an immutable
tuple for effort selectors, separate from model selection. Its values match
`CodexReasoningEffort`, including the `ultra` level served by current Codex
models. These are accepted launch values; individual models can offer fewer
levels. A configured native composer at `none`, `max`, or `ultra` has the same
readiness guarantees as at other effort levels (§5.4, C-API-28).

`env` uses the same launch-only environment overrides and removals as §5.1,
including version/update/capability probes and the agent's login shell. It is
not persisted and never changes the host environment.

Elwood sets the PTY working directory and also passes Codex `--cd <cwd>` so
Codex's own session state and the shell's current directory agree. `cwd` MUST
already be a directory, with the same `codex_start_failed` rejection, the same
check after preflight, and the same guarantees as `startClaude` (§5.1, C-API-61).

`reasoningEffort`, when set, is forwarded as the Codex `-c
model_reasoning_effort=<value>` config override so the session starts at the
requested reasoning effort. Codex validates this value SERVER-SIDE — an
out-of-enum value launches successfully and then fails at the first turn with a
provider error — so Elwood validates it against the `CodexReasoningEffort` set
BEFORE spawning and rejects an out-of-enum value with the typed
`codex_invalid_reasoning_effort` error (listing the valid values), turning a
deferred mid-session failure into a fast, clear start-time rejection. Reasoning
effort and model are independent axes programmatically (effort is its own `-c`
key); Elwood emits the reserved `model_reasoning_effort` override AFTER caller
`configOverrides`, so `reasoningEffort` wins over a hand-rolled duplicate. The
effort applies to the launched session only and is NOT persisted by Elwood (the
config-restore teardown already strips a root `model_reasoning_effort`, §5.3); a
resumed session must re-supply it (§5.6), consistent with `model`.

`configOverrides` contains raw Codex `key=value` overrides passed through
`--config` after Elwood's generated hook command config so callers can
intentionally override non-reserved Codex behavior. Callers own TOML correctness
for these raw overrides; Elwood shell-quotes each override and passes it unmodified.
It must be an array of strings: anything else, on start or resume, rejects with the typed
`codex_invalid_config_overrides` error before preflight runs or any process is spawned
(C-CODEX-03). Elwood reads a root
`model_reasoning_effort` entry only to decide what initial readiness waits for (§5.3,
C-API-28). Elwood's generated `features.hooks=true` and
`hookTrust="trust-all"` overrides are reserved and applied after caller config
overrides because enabled, trusted hooks are required for Elwood to function.
When `autoupdate` is true, Elwood runs `codex update` from the user's login
shell before spawning Codex and rechecks the version after the update. If Codex
later shows an interactive update prompt inside the TUI, Elwood skips that
prompt through PTY input, including Codex's cursor-addressed update screen.
Elwood never selects "Update now" inside the live TUI (an in-TUI update restarts
Codex out from under the session); the real update is the preflight `codex update`
above; interactive selection is limited to verified safe choices. When an update action is visible,
the safe choice must follow it in the numbered option list and must not itself
perform the update. A skip-shaped row before `Update now` is left unanswered.
Initial selection and every retry require a validated first-party update banner in
that same current frame, together with a safe numbered choice. A bannerless frame
never authorizes automation, even when its option numbers and labels match an
older update appearance. Recognition still holds queued input through partial or
bannerless replacements until positive native composer clearance; withholding a
selection does not release that hold. A clipped first-party banner without a safe
option is blocking evidence only. Generic agent prose containing "update available"
does not activate the blocker.

Elwood recognizes two native layouts of this prompt (C-CODEX-12, C-CODEX-27). Codex
0.155 draws `Update available! X -> Y`, a release-notes row and a `Press enter to
continue` footer. Codex 0.171 and later draw `Update available · X → Y`, the
`Release notes:` link, and an `enter continue · esc skip` footer, at start and on
resume. A narrow terminal wraps that link onto later rows, even mid-word. Both
layouts name the install command in the update action: `npm install -g
@openai/codex`, or for a standalone install a `curl … install.sh` command that
wraps onto indented continuation rows. Wrapped rows are compared with the exact
link and commands without their whitespace; any other link text, footer, command,
or row between the release notes and the choices withholds automation. On both
layouts the first skip-shaped choice after the action is `Skip`, ahead of `Skip
until next version`, so Elwood's answer records no dismissal in the user's Codex
update state. The boxed passive update notice Codex prints in its
transcript after a skip is not an update prompt.

After taking the key, Codex 0.171 and later first repaint the screen the prompt
replaced, and only then show the configured composer: on a start the boot composer,
a native placeholder over `? for shortcuts` with no status row, and on a resume the
`Resuming session…` placeholder. That repaint belongs to the skip (C-CODEX-27).
Queued and pre-readiness input stays held through it, it is not reported as
`codex-unidentified-dialog`, and the boot composer or placeholder is the skip's
answer, so the skip reports `startup_prompt` there. The skip owns the repaint from
the first frame without the prompt after its fulfilled key, and gives it up at the
configured composer, at another dialog or a trust gate, when the update prompt is
drawn again (a new appearance), on raw caller input, on close, 2 s after that first
frame if neither the boot composer nor the placeholder has shown, or 30 s after the
skip's answer. Giving it up any other way than at the configured composer leaves the
current frame to the retained hold below.

Codex drops a key that arrives while it paints this menu, so the first key waits
until the menu has been on screen for 500 ms. The safe numbered choice is retried
for a bounded interval, but only on a frame of the menu that Codex drew after the
last key. Elwood's frame can be older than Codex's screen, and a frame unchanged since
a key cannot show that Codex ignored it: retyping onto it could reach the screen Codex
drew after taking the key. A resize or host output that changes Elwood's frame without
Codex output is not such a frame. Retain only the current validated
first-party option block, with at most 32 options and 200 characters per label;
exceeding either bound withholds automation without releasing input. A later
validated first-party banner with a safe option block within both bounds retires
the overflowed appearance and may start one fresh bounded attempt, even for the
same version pair. Redraws of that valid block cannot renew the attempt again.
Before each write, compare the current block with the captured appearance. Changed labels,
removed safe bindings, or renumbering invalidate the old retry even before the next
frame observer runs. A bannered safe choice replacing a removed safe number starts
a new appearance rather than extending an accumulated union of old bindings.
A banner-only or action-only repaint cannot renew grace; a later unambiguous
banner with a current safe choice may establish a fresh bounded attempt.
Choices must form one current native numbered block: numbered pre-banner rows
(including clipped prefixes), duplicate or restarted numbering, unknown option labels,
and unrelated rows within or after the block withhold automation. Native update/skip/later labels,
the captured install-command continuation, release-notes header, and Enter footer
remain accepted; a recognized banner still blocks even when its option block is
ambiguous. Such a recognized-but-ambiguous frame permanently revokes its
active attempt; later bannerless choices cannot restore it. Fresh unambiguous
first-party banner evidence with a valid current safe choice starts a new attempt,
never the revoked one. Banner-only or action-only repaints remain blocked after
revocation and cannot reauthorize later bannerless choices or renew CLI grace.
It stops without another write once that generation clears or changes, and fails the
startup operation if the update prompt remains but its safe option disappears or the
retry interval is exhausted. An unknown or blank replacement permanently revokes
its attempt; bannerless choices cannot reauthorize it, and fresh first-party banner
evidence is required. Authoritative positive native composer clearance preserves
the completed attempt’s settlement. Live sessions decide clearance after the current
frame’s retained input hold is classified; composer text alone cannot restore
eligibility. One unambiguous changed first-party version banner supersedes the prior appearance
without a clear frame. Captured retries reject the changed banner before another
write; the new appearance may start its own bounded attempt. Generation-tagged
attention (§5.4) renews the CLI grace once for a replaced banner, or for fresh
unambiguous first-party banner evidence with a current safe choice after revocation,
even when the version pair is unchanged. Duplicate or stale generations and
ordinary same-banner redraws cannot extend it. Each appearance of the
update screen is its own generation: an exhausted attempt stays latched until that
screen clears, so one
persistent screen gets one bounded attempt rather than a fresh retry loop per frame,
and a completion from an earlier generation never re-arms the current one. Once a later
appearance has superseded it, an earlier attempt's late success or rejected write
settles as a quiet cancellation: only the current generation reports `startup_prompt`
or `startup_prompt_write_failed`. A write rejected after its screen has merely cleared
is quiet too (nothing is left to retry or block on), while a screen that clears after
the key was written reports `startup_prompt` only after positive native composer
clearance, or on the repaint above. Outside the repaint the skip owns, a missing reader, unknown replacement, partial frame, or retained input
hold settles quietly as cancellation even when the digit write completed. A rejected PTY write, or a safe option that has not
painted yet, stays retryable within the generation. A blocked update screen therefore becomes a bounded run
failure even when the caller supplied no whole-run timeout; delayed input cannot
reach the restored composer or a replacement dialog. This prevents a queued Enter
from selecting Codex's default "Update now" action (C-CODEX-12). Closing the session
cancels update retry timers and prevents pending automated keys from reaching the
PTY. A disposed responder starts no new attempt, and late completion or rejection
settles quietly without startup success activity or a write-failure warning.
An offer that no skip answers, because raw caller input took it over, its
retries ended or it has no safe choice, is listed as a `kind: "update"` dialog
([§5.13](5.13-dialogs.md#codex-update-offers)).

Update automation eligibility and queued-input blocking have separate lifetimes.
After a recognized update screen is replaced by an unknown dialog or partial frame,
queued input remains held until the live terminal positively identifies its native
composer and visible input cursor in a completed render with no working-title
signal. The title may be absent or contain an ordinary directory name. A bare caret
or pending render cannot release the hold. A continuously visible pre-update
composer cannot clear new replacement text above it, even with its old cursor
visible. Once verified composer evidence is lost, a newly appearing native
composer may clear the hold with newly loaded resume history. This retained hold does not start
for an unrecognized dialog without a prior update appearance. It reports
`codex-unidentified-dialog` only when no more specific blocking rule identifies
the replacement, and never while the skip owns Codex's repaint; a recognized trust gate keeps its own diagnostic rule (C-CODEX-12,
C-ATTN-03). Pending automated trust owns partial repaints without emitting the
generic retained-update label. A current human or unknown gate takes diagnostic
precedence over a retained trust label.

`strictVersionCheck` makes unparseable Codex versions fatal instead of
warning-and-continuing.

`highTrust` is the same agent-neutral "never ask for permissions" switch as on
Claude (§5.1). On Codex, `highTrust: true` expands to `sandbox:
"danger-full-access"` with `approvalPolicy: "never"` before the posture is
persisted or the process is spawned. Supplying an explicit `sandbox` or
`approvalPolicy` together with `highTrust: true` is a configuration error
rejected before spawn with the typed `codex_high_trust_conflict` error.

`autotrust` is an opt-in convenience for embedded/headless parent apps.
When true, Elwood detects Codex's first-party directory trust prompt in the
rendered terminal and chooses the trust/continue option through PTY input,
emitting `startup_prompt` activity with label `workspace_trust`. The default is
false because trusting a workspace is a security-sensitive decision. Independent
of `autotrust`, Elwood launches Codex with session-wide hook trust bypassed.
This trusts ALL configured Codex hooks, including third-party hooks, so the
required Elwood hook bridge can function. If a `Hooks need review` prompt still
appears, it is answered once, emitting `startup_prompt` activity with label
`hook_trust`.

`persona` behaves exactly as specified for Claude in §5.1: enqueued before
control returns to the caller, delivered as the first user message on the first
ready transition, never persisted, and never re-sent on resume.

Speed options and raw override behavior are specified in [§5.11](5.11-speed.md).
