## 5.10 Native questions

`ElwoodAgentSession`, both raw adapter interfaces, and both lazy session classes
expose `listQuestions(): Promise<readonly ElwoodQuestionRequest[]>` and
`answerQuestions(requestId, answers, options?): Promise<void>`. These controls
bypass the ergonomic turn queue; answering never creates a user turn or finishes
an existing `send`/`stream`. Lazy controls start the session before delegation.

A request has readonly `id`, `agent`, `delivery` (`blocking` or `queued`), and
ordered `questions`. Each question has readonly `id`, `prompt`, optional `header`,
`options` (ordered readonly `id`, `label`, optional `description`), `selection`
(`single`, `multiple`, or `none`), `textMode` (`none`, `alternative`, or
`additional`), and `supportsSecretInput`. IDs are opaque and scoped to the live process.
`alternative` permits text instead of options; `additional` permits text alongside
options. Capabilities describe only supported native input, not model intent.

The snapshot lists currently available requests in discovery order and is deeply immutable.
Redraws and mirrored source records retain identities. A semantic replacement
closes the old request as unavailable and raises a new ID. No question or answer
is stored in Elwood session state or restored by Elwood on resume.

`question` events carry `elwoodSessionId`, `agent`, `request`, and `phase`
(`raised` or `closed`). Closed events also carry `reason`: `answered`,
`cancelled`, or `unavailable`. `answered` requires native acceptance evidence;
`cancelled` requires native dismissal evidence; withdrawal, turn end, replacement,
and shutdown use `unavailable` when no stronger evidence exists. Matching
normalized activities have `kind: "question"`, `source: "terminal"`, the same
structured event in `question`, and a phase label. They contain request prompts,
not answer values. Existing raw hook/transcript observations remain unredacted.
Question activity is telemetry and never ergonomic answer text. The request, event
and normalized activity agents agree, including in their public discriminated types.

Each answer contains `questionId`, optional ordered `optionIds`, and optional
`text`. Exactly one answer for every question in the selected request is required.
Unknown/duplicate IDs, unsupported text, multiple options on single-select,
empty answers, and control-bearing text reject as `invalid_question_answer`
before any write. The complete validated answer batch is limited to 8 MiB: the sum of UTF-8 bytes
in its question IDs, selected option IDs and text. JSON syntax and unknown fields
do not count toward this limit. Malformed UTF-16 is rejected. Multiline text is safely bracketed-pasted. An unknown, closed,
retired, or previous-process request rejects as `question_not_found` before input.

`options` accepts optional positive finite `timeoutMs` (default 20,000) and
`signal: AbortSignal`. Long deadlines use bounded timer chunks. A single answer transaction owns the physical question
input lane; overlapping calls reject as `question_answer_failed` before reading
caller answer or options fields, including stale IDs and invalid batches. When
no attempt owns the lane, unknown or retired IDs reject as `question_not_found`
before input. It operates
even while an ordinary queued writer or ergonomic turn is waiting. Every write
revalidates current completed native frames, live request ownership and caller
intervention. Raw keys and interruption revoke the transaction. Timeout,
cancellation, changed/unsupported layout, rejected input and uncertain acceptance
reject with content-free `question_answer_failed`; a submitting Enter is never
blindly retried. Closing the session prevents further writes. Failures may expose
only fixed `details.phase` categories: `frame_wait`, `adapter`, `terminal_write`,
`native_acceptance`, or `revoked`; they never retain raw exceptions or answer text.

A failed attempt that has not started a physical write can remain answerable. If
input may have reached the CLI and native acceptance is unconfirmed, the API
request closes once as `unavailable` and disappears from snapshots. Retrying its
ID rejects as `question_not_found` before input. Elwood retains the native identity
and holds ordinary automation until correlated native closure, turn end or
shutdown releases it. Redraws, changed metadata for that same reserved identity
and late write completion cannot republish or reauthorize the request. Native
closure releases this reservation silently, without a second question closure.
The API closure alone does not mean the CLI is ready for ordinary input.

Pending requests and native question editors hold ordinary prompt, command,
loop and login writes. Native lifecycle status remains independent of queued
question availability. Unknown question layouts are hold-only, observable through
the existing terminal/attention surfaces, and never receive guessed keys.

Claude `AskUserQuestion` hooks supply grouped request metadata. A request is
published only when its matching native questionnaire is visible; direct caller
hook answers and denials retain precedence and do not create a phantom pending
request, even if a matching stale screen is still visible. Initial hook activity
keeps its existing timing; discovery waits for that exact caller decision and
then a fresh completed native paint.
Overlapping Claude hooks retain independent native tool-use identities and exact
caller outcomes, including out-of-order resolution and completion. A pending
outcome withholds only its matching candidate; it cannot suppress discovery of an
unrelated resolved request. Matching `PermissionRequest` mirrors retain the
original candidate even when their hook IDs differ. A native panel that matches
multiple independent candidates grants no answer authority; ownership remains
held until native evidence disambiguates it. ID-less completion requires one
uniquely matching candidate and cannot retire an ambiguous group.
The adapter supports the captured single-choice, checkbox, tabbed sequential
question and review stages, with alternative free text. It requires a recognized
initial first-question stage; a human-navigated unsupported partial stage rejects
safely. Only a matching `AskUserQuestion` completion acknowledges the whole
request. A supplied native completion ID must match the active request; without an ID,
ordered question definitions must match its prompts, headers, selection modes and
ordered option labels/descriptions. Unrelated tools or mismatched question
metadata cannot acknowledge, cancel or retire that request. The standard hook
timeout is unchanged and never waits for a human answer.


Codex native text acceptance normalizes CRLF and CR to LF, then trims Rust
Unicode White_Space at both ends (U+FEFF is retained); interior whitespace is
preserved. Queued selected labels are trimmed; modal selected labels remain
exact and optional notes use the text normalization. Long, clipped, multiline and literal placeholder text is accepted only while
the submitted text remains in the same native question editor. The complete
committed native answer must match the submitted answer before success.
Unsupported or opaque Codex native identities reserve ordinary automation until
explicit native turn end; raw human terminal input remains available.
Codex metadata budget overflow emits one content-free `question_automation_disabled`
warning and normalized warning activity per session, then disables automation.

A successful Claude final submission awaits matching native completion through
a newly empty composer. An interrupted, unconfirmed answer retires the API
request while retaining its native identity and input hold until native closure;
a later acknowledgement releases that reservation without another closure event.

Question notification failures are contained without changing request state or
native input holds. The first failed question or companion question-activity
observer in a live session produces the content-free `question_observer_failed`
warning and normalized warning activity specified in [§5.4](5.4-events.md).
